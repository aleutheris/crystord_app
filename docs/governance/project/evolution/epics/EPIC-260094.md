# EPIC-260094: A removed label keeps filtering every later search

- Epic ID: EPIC-260094
- Title: A removed label keeps filtering every later search
- Persona/Actor: Any user who runs a label search and then browses by category.
- Value statement: For a user combining label search with category browsing, make the query the
  app runs match what the search bar shows.
- Context: Reported by the owner 2026-09-16. After a label search earlier in the session,
  selecting `business ▸ leads` returned one atom and other category values returned none. It
  looked like a 9.4.0 backend regression and is not: the engine returned 3/3 tagged atoms through
  its real GraphQL schema with the app's exact `RetrieveAtoms` document. A reload clears it
  (search state is memory-only).
- Problem statement: submitted labels live in `searchLabelsRef` (`use-graph-data.ts:50`) and change
  only on submit (`use-search.ts:53-67`). Category clicks reuse them by design (ADR-260071:
  `undefined` = reuse). But removing a label — chip `×` / recommended-label toggle (`toggleLabel`),
  Backspace (`removeLastLabel`), or Clear (`clearFilters`) — only changes local state, so the
  removed label stays in every later query. Clear also hides the summary that would reveal it.
- Evidence: code reading plus the owner's reproduction and workaround. Not yet reproduced in a
  test; T1 does that before the fix.
- Expected outcome: removing a label that was part of the last search re-runs the search without it.
- Success metric(s): T1's scenario passes after T2 and fails without it.
- Non-goals: persisting search state; auto-running on add; redesigning the search bar; the engine's
  unselective-`retrieve` crash (engine EPIC-260099).
- Constraints: ADR-260071's reuse contract is unchanged; the fix stays in `use-search.ts`.
- Dependencies: ADR-260071.
- Target window: next.
- Validation approach: T1 (e2e) + T2 unit tests.

## Ideation Bullets

Resolved 2026-09-16; the owner asked for the most minimal option on each.

- [x] **Removal re-runs the search only when it removes a *submitted* label**, re-submitting the
      remaining submitted labels. Applies to all three paths (`toggleLabel` only when it removes).
      Removing a chip that was never submitted fires nothing.
- [x] **Adding still requires ▶.** Re-submitting `submittedLabels` (not `selectedLabels`) keeps that
      true.
- [x] **Summary: no change.** It derives from `submittedLabels`, which is now always the last query run.
- [x] **No extra check, no ADR.** T1 is the regression guard.

## Learnings

- **Two reviews.** An adversarial review (3 lenses, each finding checked by a skeptic) and the
  owner's implementation review. Fixed as a result: the "Clear fires nothing" test could not tell
  the correct guard from a plausible wrong one (`hasSubmitted`), so it now runs an empty search
  first; Clear's re-run is now asserted end to end, not only described in a comment; and one test
  name described a throw it never checked.
- **Filed as follow-up, not rejected: EPIC-260095.** Overlapping searches can land out of order,
  because `fetchAtoms` keeps whichever response arrives last (`use-graph-data.ts:83`). The race is
  older than this epic, but this epic made it easier to hit: before, only quick category-chip
  clicks could trigger it; now holding Backspace over three or more submitted chips does too, and
  the stale result is the same invisible narrowing this epic removed. The fix belongs in
  `use-graph-data.ts`, outside this epic's approved scope.
