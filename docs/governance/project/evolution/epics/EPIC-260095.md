# EPIC-260095: An older search result can overwrite a newer one

- Epic ID: EPIC-260095
- Title: An older search result can overwrite a newer one
- Persona/Actor: Any user who changes the search or category filters in quick succession.
- Value statement: For a user refining a search, always show the result of the latest query.
- Context: Filed 2026-09-16 as a follow-up from EPIC-260094's implementation review.
- Problem statement: `fetchAtoms` (`use-graph-data.ts:60-94`) keeps whichever response arrives last
  (`setAtoms` at `:83`) and never checks whether a newer request has started. When searches
  overlap and an older response arrives last, the graph shows results for a query that is no longer
  on screen. Each request also turns the loading indicator off in its own `finally`, so it can
  switch off while a newer request is still running. Later queries still send the right filters,
  because the stored labels update when each request starts. Triggers: quick category-chip clicks,
  a mutation refetch overlapping a search, and, since EPIC-260094, holding Backspace over three or
  more submitted label chips.
- Evidence: code reading (EPIC-260094's adversarial review and the owner's review). Not reproduced.
- Expected outcome: only the latest request's response updates the atoms, error and loading state.
- Success metric(s): a test in which an older response arrives after a newer one leaves the newer
  result on screen, and fails without the fix.
- Non-goals: debouncing input; cancelling requests on the server; changing what any query sends.
- Constraints: the `search()` contract (ADR-260071) is unchanged; the fix stays in `use-graph-data.ts`.
- Dependencies: EPIC-260094.
- Target window: TBD.
- Validation approach: a unit test with controlled response order; reproduce first.

## Ideation Bullets

- [ ] Guard mechanism: a request counter that ignores superseded responses (smallest), or
      cancelling the superseded request.
- [ ] Should mutation refetches (create/update/delete) follow the same latest-wins rule? They go
      through `fetchAtoms`, so a single guard covers them unless we exclude them on purpose.
